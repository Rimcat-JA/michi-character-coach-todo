## Catalog change submission checkpoint

## Windows CI ownership check and automatic catalog submission checkpoint

Windows CI initially rejected the pipe ready message even though the protected DACL had one rule and the helper had no stderr. The check incorrectly required the numeric SID to appear literally in SDDL; Windows can use aliases such as `LA` for local Administrator ([Microsoft SID strings](https://learn.microsoft.com/en-us/windows/win32/secauthz/sid-strings)). The relay now reads the owner and the only access rule as SecurityIdentifier objects, verifies both equal the current SID, and requires a non-inherited Allow/FullControl rule. Main requires these verified flags in addition to the protected DACL and remote-client rejection. No ACL or execution-policy bypass was added. Bounded startup diagnostics contain only fixed categories/type/numeric codes, never protocol bodies or credentials. Commit `889eb33` passed both Ubuntu and Windows in Actions run `37046580955`.

Catalog submit now asks the running renderer to process that exact command ID with a client-scoped gateway. This internal request is absent from the remote catalog. The existing signed inbox, N09 policy, per-client delegation/bounds/quota, main lease and atomic bus receipt decide application. Protected fields, outside-auto bounds, exhausted automatic quota and busy native reviews stay awaiting approval. Background work never changes the UI's selected client; it does not replace a native review already in progress. Scoped authority clearing also removes only the corresponding S21 received metadata, and a saved command stops appearing as merely received. Auto grants can include separately shared protected fields; actual automatic payloads remain strictly notes/date only and protected values still require owner confirmation. Another current owner export is required after task revision changes; no automatic export overwrites edited copies.

## Verified basis real-route and scenario ledger checkpoint

Verified `app_instruction` references now use the real native registry/DB/ref/epoch path. `authorizeRequest` calls `verifiedExternalInstruction` inside the existing plan transaction (made transaction-safe with `Dexie.waitFor`) and passes the result into the pure gate, instead of blanket-rejecting every non-`external_request` basis. A valid native-issued ref can prepare to `awaiting_approval` through the shared signed inbox and native value confirmation; it never auto-applies. Fake refs, cross-context refs, tampered payloads, and `verified_detection`/`approved_rule_instance` without a real issuance path still fail closed with `UNVERIFIED_REFERENCE`. No authority is minted from tool arguments, and persisted instruction metadata alone cannot recreate runtime approval after restart/restore.
